## 3. FNOP analysis vs the RTL
Holds:
- `DATA_EXH` (`wf68k30L_top.vhd:530-532`) writes `PC(15:0) & STACK_FORMAT & "00" & IVECT_OFFS` at STACK_POS = 4.
- `STACK_CTRL` (`wf68k30L_exception_handler.vhd:688-725`) sets format 0 for EX_1111, A/B for BERR/AERR (IBOUND), 1 for the throwaway frame.
- RTE accepts 0/1/2/9/A directly and B after the version word check (`:899-925`); anything else is a format error (exception 14).

Does not hold / gaps:
1. **"xB" does not prove the format nibble was bad.** EX 14 also fires for a correct `B` frame whose
   version word at SP+$36 is not $1904 (`EXAMINE_VERSION`, `:918`). And a format A/B RTE does not "return to
   the patched PC": a real 68030 reruns the faulted cycle/instruction from the frame's internal state. So probe 3
   ("RTE ignored the patched PC") is what a correct B frame does. The probe's `MOVE.L A2,2(SP)` skip only works for
   a format 0 Line-F frame.
2. The open question is **why FNOP took vector 2 on the board at all**. A real 68030 without an FPU runs a CPU-space
   coprocessor cycle, gets BERR and turns it into Line-F (format 0). This core issues no CPU-space cycle (per sim), so
   the BERR came from somewhere else.
3. `STACK_CTRL` only loads format/position on the *entry* into BUILD_STACK. If EXCEPTION changes from EX_1111 to
   EX_BERR while already in BUILD_STACK (bus error during Line-F stacking), STACK_FORMAT_I stays 0 and the countdown
   continues: a mixed frame with vector 2. Candidate; check how BERR during stacking is handled (double fault).

Candidates for a wrong frame at STACK_POS = 4 (ranked):
1. A BERR from the bus (unmapped ST address, e.g. a probe of the SFP004 at $FFFA40, or the probe's own accesses)
   rather than from FNOP, followed by an RTE that fails the format B version check or reruns a cycle the probe did not expect.
2. A BERR during Line-F stacking (point 3): format 0 frame body with vector 2.
3. Board-only timing: FAST_HANDOFF + BRIDGE_EARLY_AS were never simulated with this sequence. Cheap A/B: build with
   either switch off and re-run fnop.prg; and run tb030 with FAST_HANDOFF=1 (copy the core with the top default set
   to 1 and pass `WF_SRC`, as done for the F65 check).
4. Write-data capture (WP_BUFFER at START_CYCLE) vs STACK_POS update: unlikely, because it would break every frame and TOS runs.

Next steps (cheap, read/measure first): put the probe source in the repo; have the probe print the whole frame
(format word, vector offset, $36 version) on the board; A/B the two switches; sim tb030 with FAST_HANDOFF=1.
