WHAT: Patch 1 of the WF68K30L request handoff (F65). A completing prefetch long can roll S5 straight into S0 of the next prefetch long. Operand cycles are unchanged. The switch is off.
WHY: A real 68030 starts the next cycle on the edge after S5 when a request is pending. This core already does that between the halves of a sized long (31 ns). Between separate transfers it inserts IDLE and START_CYCLE (156 ns). This patch removes those two clocks for prefetch-to-prefetch only.
LOOK FOR: Nothing on the board yet. The define is commented out, so a normal build is still the early-AS image. Do not flash this until run_rtl.sh has passed with the generic on.

Switch: `WF030_FAST_HANDOFF`, written by build_st_helper.tcl into build_sel.vh, VHDL generic FAST_HANDOFF (default 0). BRIDGE_EARLY_AS is untouched. Uncomment the define to build the new path. Delete the BRIDGE_EARLY_AS line to measure this fix alone.

What it does, with the switch on:
- Armed on the edge that leaves S3, one clock before the cycle ends (wf68k30L_bus_interface.vhd, P_PF_CHAIN). Registered. No path back through BUS_BSY.
- On the S5 edge the decoder stays in DATA_C1C4, the slice counter rolls to S0 (the same rollover a sized long already uses), SIZE reloads to a long, ADR_OFFSET clears, OCSn pulses, the queue re-arms F_CUR/F_ADR.
- Fires only when this prefetch will finish, the stream is valid, the queue has room (Q_CNT <= 2), and DATA_RD/DATA_WR are 0. HALT, bus grant, retry, bus error, a queue miss, a pipe flush and RMC take the old IDLE path.

Deviation, honest: PF_REQ cannot be true on this edge, because INFL is still 1, and after the long is queued Q_CNT is usually 2 so the queue's own Q_CNT <= 1 refill would not start another long yet. The chain starts that long one step earlier, while the pipe has room. The words are the stream the queue already owns (F_ADR). Operand cycles still take IDLE then START_CYCLE. That is patch 2.

Not run here: this machine has no GHDL and no gw_sh. Do not treat this as tested.
